## 评委问答准备

### Q1：这和现有的 AIR（AI Receptionist）有什么关系？

> AIR 解决的是客户来电路由——它是前台。AgentRun 解决的是路由之后的每一步——它是后台。两者是互补关系，不是竞争关系。Keller 的 AIR 已经把等待时间从 12 分钟降到 90 秒，但路由之后的派单、传真、投诉处理仍然是人工的。AgentRun 填这一层。

### Q2：为什么企业要把这么重要的事情交给 AI 执行？

> 因为执行是有人监督的。每一个 ACTION 都记录在 Control Plane 的审计轨迹里。高风险操作（跨部门通知、传真、外呼）需要人工确认（audit notice / OOB approve）。Bot 的角色是"准备好，等人点头"，不是"自主决定"。Karen 输入 `/lowes-batch send` 之后，传真才发出——这一步是人的。

### Q3：Agent-to-Agent 会不会失控？

> 不会，因为路由是声明式的。每个 Bot 的 SOUL 里明确写了"我接受来自哪些 Agent 的路由，我向哪些 Agent 发路由"。Bot B 不会响应任意 Bot A 的消息——只响应 source_user_ids 里预配置的可信 Agent。路由拓扑是运维时决定的，不是运行时随机产生的。

### Q4：和 MuleSoft / MuleRun 有什么差别？

> MuleRun 建了一个新 IM 平台，Agent 在里面讨论。我们利用 RC Team Messaging（用户已有的 IM），Agent 真正执行。关键差异：MuleRun 的 Agent 说"我建议发传真"，我们的 Agent 说"传真已发，FAX-REF: 20260603-031，在台账里"。这个差异来自 RC 的 Phone/SMS/Fax API，MuleRun 没有这些。

### Q5：如果 RC 用户不是安装公司怎么办？

> SOUL + Skill 是可配置的。Keller 是验证案例，但 Skills 是通用模块：`pto-routing` 适用于任何有 HR 的公司，`payment-reconciliation` 适用于任何 B2B 服务商，`complaint-handling` 适用于任何有客户服务的公司。角色 Bot 的框架是通用的，具体的 Domain Knowledge 按行业填充。

### Q6：现在有多少是真正实现的？

> FIJI Onboarding → Control Plane → K8S → RingClaw Pod 这条链路已经实现。PHONE_CALL → FIJI directCall 这条最近的 commit 已经实现。我们在 Hackathon 里完成了 SOUL/Skill 系统设计、Bot 配置、路由协议设计，以及修复了代码里两个编译错误。距离完整生产还差约 500 行代码（inbound wire + OOB 反向通道），这是清晰的技术路径，不是未知问题。
